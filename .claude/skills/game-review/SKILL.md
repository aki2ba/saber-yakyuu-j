# ゲーム開発レビューフロー（game-review）

出典: `thyroxin/research/game_dev_philosophy_research_20260724.md`（宮本茂/桜井政博/Sid Meier/
宮崎英高/Valve/Cerny/Supercell等の思考法調査）。本スキルはその Part 3 を実行可能な手順に固定
したもの。背景・出典の詳細が必要なときだけ研究レポートを読む（通常は本スキルだけで完遂する）。

## モード判定

引数・文脈から3モードのいずれかを選ぶ（不明なら AskUserQuestion ではなくフルレビューを既定に）:
- **着手前チェック**（`pre <機能名>`）: フェーズ①＋観点12。specを書く前に実施
- **実装後チェック**（`post <機能名>`）: フェーズ②③④のうち該当する観点。コミット前に実施
- **フルレビュー**（引数なし / `full`）: 全フェーズ。現行ビルド全体を対象に定期実施

## 15観点の物差し（全モード共通の判定基準）

| # | 観点 | 合否の目安 |
|---|---|---|
| 1 | 面白さの核は3行で言えるか | 三原則(req_2)のどれを強化し、既存調査の弱点仮説のどれを埋めるか3行以内で言える |
| 2 | 単体で「おもちゃ」として成立するか | 勝敗・目的を外しても当該画面を5分いじって楽しい |
| 3 | 初見5分で何が起きるか | 操作説明なしで迷わず次の行動が分かり、5分以内に采配/育成の核に触れる |
| 4 | 教える単位が分解されているか | 安全な提示→応用→組み合わせ→卒業の順。初出時に一気に全部見せない |
| 5 | 意思決定にリスク/リターンがあるか | 「常に同じ選択が最適」というドミナント戦略が無い。トレードオフが画面で提示される |
| 6 | 失敗の自己帰属性 | 負けた理由を1秒で自己説明できる（WPAカード・コラム等で追える）。説明不能=設計バグ |
| 7 | 観察優先・思い込みで蓋をしない | 数値ゲートPASSに加え実プレイ/実況ログ目視で「あれ？」が無い |
| 8 | 触った瞬間の手触り | 選択→結果の因果が1アクション以内に文言/色/バッジで見える（数値だけにしない） |
| 9 | 1機能が複数の弱点を同時に解決するか | 弱点仮説リストの2つ以上に効く（局所対症療法の連打でない） |
| 10 | 情報は必要な時に必要な場所にあるか | モバイル390px幅で各タブ1〜2画面。判断に不要な情報が常設されていない |
| 11 | 同時に教える新規情報は1つか | 初出画面で初見の用語/数値/操作が同時に2つ以上出ない |
| 12 | プロトタイプでGo/No-Go判定したか | specに「最小の1本を通してから横展開」の順序が明記されている |
| 13 | スコープをセルフkillできるか | 効果が薄い機能をサンクコスト無視で中止/フラグOFF撤退できている |
| 14 | 波形の緊張管理か | 山場（特別デー/接戦）と平常が交互に来る。均質な日々が長く続かない |
| 15 | 成功・失敗を数字と共に言語化したか | progress.mdが「やったこと」列挙で終わらず、良かった点/課題点が数字付き |

## 実行手順

### 着手前チェック（pre）
1. 対象機能について観点1を書く（3行）。書けなければ「保留・再設計」と報告して終了
2. 観点9: `thyroxin/research/fun_theory_research_20260720.md` と `baseball_game_mechanics_research_20260723.md` の弱点仮説と照合し、効く仮説を列挙
3. 観点12: 最小の1本（1シナリオ通し）の検証手順を1-2行で決める
4. 結果をspec冒頭の「## レビューチェック（着手前）」節に記入

### 実装後チェック（post）
1. `npm run build` → `dist/pennant.html` の実プレイまたは `tools/smoke-ui.mjs` 相当のヘッドレス操作で対象機能を実際に触る（観点7: 数値ゲートPASSだけで済ませない）
2. 該当観点を判定:
   - 新規UI/モーダル → 観点3/4/11（初見の同時新規要素を数える）
   - 判断系機能（采配/育成/市場） → 観点5/6（ドミナント戦略の有無は calibrate の発現帯分布で裏付け）
   - 表示層 → 観点8（選択→結果の因果の見え方）・観点2（おもちゃ性）
3. 結果を progress.md エントリに「## レビューチェック（実装後）」形式で記録（観点15: 良かった点2-3・課題点1-2を数字付きで）

### フルレビュー（full）
1. **初見体験（観点3/4/11）**: 新規ゲーム開始から5分ぶんの操作を「肩越しの視線」で実施。
   可能なら Playwright（`/opt/pw-browsers/chromium`・`dist/pennant.html`）でスクリーンショットを
   撮りながら、初見プレイヤーとして迷った箇所を記録。開発知識を持たない体で操作すること
2. **意思決定の質（観点5/6）**: 采配介入・トレード・育成方針・週次目標の各選択画面を列挙し、
   それぞれ「トレードオフの提示」「失敗の追跡可能性」を判定
3. **手触り（観点2/8）**: 主要画面を目的なしで触り、おもちゃ性と因果の見え方を判定
4. **情報設計（観点10）**: Playwrightで主要タブをモバイル390px幅でスクショ＋scrollHeight実測
   （`thyroxin/research/ui_ux_review_20260707.md` と同手法）
5. **長期ループ（観点13/14/15）**: progress.md直近10エントリと specialDays/週次目標の発火頻度を確認
6. **報告**: 観点番号付きの発見リスト（重大度順）＋改善提案（各提案に観点9の「何個の弱点に効くか」を付す）。
   結果は `thyroxin/reviews/game_review_YYYYMMDD.md` に保存し、progress.md にエントリを追記

## 鉄則（レビュー中も厳守）

- レビューは観察と記録のみ。修正はユーザーまたはオーケストレータの判断を経てから別作業として行う
- 真値(trueAbility)を「見えている前提」で評価しない（プレイヤーは観測とスカウト等級しか見えない）
- 較正・決定論のゲート（npm test / calibrate / realism）はレビューの代替ではなく前提（観点7）
- 提案には必ず「どの観点への違反か」「三原則のどれに効くか」を付す（根拠なき好みの指摘をしない）
