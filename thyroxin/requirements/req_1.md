# 架空選手ペナント・シミュレーション 設計ドキュメント

> セイバー指標ベースの野球シミュレーションゲーム設計まとめ。
> 架空選手約1000人・ペナント運用・多年キャリア・iOS/Android展開を前提とする。
> 本ドキュメントは、これまでの設計議論の要点を実装レベルで再構成したもの。

---

## 0. プロジェクト概要

- **コア**: 実在の名前を一切使わない架空選手約1000人（例: 30球団 × 33人 = 990人）でペナントを回す。
- **売り**: 打撃・走塁・守備・投球をセイバー指標モリモリで算出。UZR / WAR まで自然に出る。
- **哲学**: 指標を「後付けで盛る」のではなく、**打席・打球単位でシミュレートした副産物として指標が自然に湧いてくる**粒度で設計する。これが全体を貫く原則。
- **展開**: 最終的に iOS / Android アプリ。まず自己完結HTMLで核を固める。
- **既存資産**: 検証済みエンジン（Node.js）＋UI付きHTML（`pennant.html`）が既に存在。較正済み（§18参照）。
- **トーン設計**: 栄冠ナイン的な育成のエモさ ×  セイバーの硬派さの融合。日本語ネイティブ。

### 法的前提（パブリシティ権）
- 実在選手の氏名・肖像・その「もじり」は、本人特定可能ならパブリシティ権侵害リスク（ピンク・レディー事件 最判平成24年）。野球ゲームはキャラクター商品型に該当する有力見解あり。
- **寄せるほどリスクが上がる**構造。個人開発で正規許諾（選手会・機構ルート）は非現実的。
- **結論: 完全架空でいく。** 本ドキュメントで実在選手名が出るのは「再現したい"現実の現象"の参照」としてのみであり、ゲーム内キャラクターとして使うためではない。

## 1. 設計の根本思想

すべての「リアルさ」はこの1点に集約される：

> **個々の選手の未来は予測不能。合わせるべきは「集団の分布」。**

- ある28歳が来年ブレイクするか故障するかは原理的に予測不能（プロの球団でも当たらない）。
- しかし選手990人を束ねた「形」——ピーク年齢・衰え速度・故障率の分布——は統計的に安定。
- 従って**リアルさ = 各選手の予測精度 ではなく、リーグ全体の分散とカーブの形**で決まる。
- **ノイズは消すものではなく、正しい大きさで乗せるもの。** これが20年来の到達点。

### 三層構造（最重要の実装パターン）
選手は以下を分けて持つ：

1. **真の実力（隠しパラメータ）** — 本人が内部に持つ本当の能力。
2. **観測成績** = 真の実力 + 打席ノイズ（＋出場機会による偏り）。プレイヤーや球団AIが見る数字。
3. **球団の評価値** = 真の実力 + スカウト誤差（球団ごとに癖・ノイズが違う）。

この三層のズレこそが、育成からの這い上がり・戦力外復活・割安選手といった**ドラマ全部の源泉**。個別は予測不能なのにリーグ全体は毎年リアル、という手触りが出る。

### 較正の目安（現実のMLB/NPBレンジ）
- 打率 .250前後 / OBP .320前後 / SLG .400前後 / wOBA .320前後
- ERA 4.2前後 / K% 22-23% / BB% 8-9%
- 総WAR ≈ (チーム数×36前後)、野手:投手 ≈ 55:45
- WARリーダー 野手8-10 / 投手6-8、UZR上位 +30前後（ただしノイズ大）

## 2. 選手データモデル（能力の持ち方）

能力を「一個の総合力スカラー」で持つのは禁物。**現実の選手像を書き分けるには、パラメータを軸ごとに割る**必要がある。これが本作の背骨。

### 2.1 最上位: 登録区分
- `role: pitcher | fielder`（投手登録／野手登録）
- ただし**能力素材は登録に依らず常時両方保持**（→ §14 転向で重要）。
- 大谷型の二刀流は「両登録を同時アクティブ」という前提破りの特殊ケース（→ §20 保留）。

### 2.2 共通素材（ポジション・登録に依存しない本人の持ち物）
| 素材 | 用途 | 加齢特性 |
|---|---|---|
| Speed（走力） | 走塁・守備範囲のスピード成分 | **早く落ちる** |
| Arm（肩） | 送球・投手なら球速の素地 | 中間（割と長持ち） |
| Hands（手／確実性） | 守備エラー回避・コンタクト素地 | 安定 |
| Reaction（反応・初動） | 守備範囲の初動成分 | やや弱い |
| Power（生体パワー） | 打球速度EVの素地 | **20代で天井、以後維持〜微減** |

### 2.3 打撃系
- **EV適性（打球速度ポテンシャル）** = 生体Power × スイング効率。※スイング効率は用具・メカニクスで動く余地あり（→ §12.3）。
- **LA適性（打球角度の最適化スキル）** — 同じ強さの打球をどの角度帯に集められるか。**技術寄り＝加齢に強い・後天的に伸びうる**。
- **方向適性（引っ張り／流し傾向）**
- **コンタクト資質** — 芯を食う頻度。技術寄り。
- **選球眼** — 四球を選ぶ・悪球に手を出さない。**加齢でむしろ伸びる**。
- **コース別ホット/コールドゾーン**（球種格子の段階2以降、§4）

### 2.4 投手系
- **球速**（mph実数。レーティングとは別枠。若いと伸び、加齢・故障で落ちる）
- **球種構成** `{fastball, slider, changeup, fork, ...}` 各球種に個別レーティング（現在値／潜在値）
  - 各球種は (空振り寄与, 被弾寄与, コンタクト質寄与) の別プロファイルを持つ ← **空振り率と被弾率は別能力**
- **制球（Control）** — コースに集める。技巧寄り＝加齢に強い。
- **スタミナ** — 何球投げられるか（先発可否のイニング耐性軸、§16）
- **GB%（ゴロ率）** — 打たせて取るタイプ

### 2.5 野手守備系（→ §13 で詳述）
- 共通素材（Speed / Arm / Hands / Reaction）＋
- **ポジション別習熟テーブル** `{C:30, SS:70, 2B:55, 3B:50, LF:60, ...}`（経験で上下、新ポジションは低スタート）
- **ポジショニングIQ** — 経験・技巧寄り＝加齢に強い
- **フレーミング**（捕手専用）

### 2.6 走塁系（→ §11）
- Speed（共通素材と共有）
- **Steal（盗塁技術）** — スタート・スライディング。足の速さと別物
- **走塁IQ** — 進塁判断。経験で伸び、加齢に強い

### 2.7 キャリア・パラメータ（→ §12）
- `peakAge`（ピーク年齢／個体ごとに分布から引く）
- `declineRate`（衰え速度／能力タイプと相関させて引く）
- 故障歴、ブレイクイベント履歴

## 3. 打席・打球解決エンジン（コア）

### 3.1 対戦の基本合成
- 打者能力 vs 投手能力を **log5 / オッズ比** で合成し、各結果の確率を出す。
- RNGは**線形合同法（決定論的）**＋Box-Muller（正規乱数）。
  - **決定論であることが後で効く**: 同一シードなら誰が回しても同じ結果 → 全国対戦のチート検証に使える（§19）。

### 3.2 EV/LA/方向モデル（打球生成の組み替え）
**現行の「結果を先に決めてゾーンを後付け」を逆転させる。** 接触した瞬間に打球3要素を先に生成し、そこから結果を導く（Statcast/バレル的発想）。

1. **EV（打球速度）** = 打者EV適性 × 投球の質 × 芯度（ミート抽選）
2. **LA（打球角度）** = 打者LA適性 × 投手GB%との相性
3. **方向** = 打者の引っ張り/流し × 投球コース

→ EV×LA の格子で「バレル / 快音 / 詰まり / 打ち損じ」に振り分け、安打確率・長打確率を決定（Statcastヒット確率グリッドの近似）。

**この組み替えが一粒五度おいしい理由**:
- 方向 = スプレーチャート、角度 = LA、速度 = EV が「結果を出すための入力」として自然に必要になる（飾りでなく計算の本体）
- 好守/拙守の判定（§13 OAA）がこの落下点から解ける
- 走塁の進塁判断（§11 UBR）が打球の質から解ける
- 対ストレート成績等（§4）が球種別ログの集計として湧く

### 3.3 対戦巡目（time-through-order）
- 打者は同じ投手を1試合に複数回見るほど打つ。**2巡目・3巡目で成績悪化**。
- この劣化幅を**球種数で重み付け**する（§16の先発可否の核）:
  - 少球種 → 巡目劣化が急（的を絞られる）
  - 多球種 → 巡目劣化が緩やか
- リリーフは基本1巡しか見せない → 巡目劣化が発動する前に降りる。

## 4. 球種格子（段階導入）

能力を球種×コース×球質の格子で持つ。**「落ち玉を覚えて開花（千賀型）」の正体 = 球種という"列が一本生える"** こと。総合力+10より圧倒的にリアル。

### 段階1（費用対効果 最大・まず入れる）
- 投手: 球種ごとに (空振り寄与, 被弾寄与, コンタクト質)
- 打者: (対速球, 対変化球) の2軸
- これだけで出るもの: **対ストレート成績**、**フォーク習得で開花**、**球種構成＝投手タイプ**、**先発/リリーフ適性**

### 段階2（余力）
- コース（ホット/コールドゾーン、3×3 or 5×5）
- 内外の苦手・配球の読み合い・弱点露呈/克服

### 段階3（沼・後回し）
- 配球AI（投手が穴を突く／打者が球種を張る）＝読み合い

> ⚠️ 段階1だけで体感が激変する。2以降は面白いが無限に深掘れるので、まず1で手応えを見る。

## 5. 打撃指標

打席結果の積み上げから自然に算出：
- AVG / OBP / SLG / OPS
- **wOBA** = (wBB·BB + wHBP·HBP + w1B·1B + w2B·2B + w3B·3B + wHR·HR) / (AB+BB+HBP)
- **wRAA** = ((wOBA − lgwOBA) / wOBAscale) × PA
- **wRC+**（リーグ平均100基準）
- K% / BB% / ISO / BABIP
- 対球種別成績（球種格子ログの集計、§4）

## 6. 走塁指標

走塁は**3つの別能力の寄せ集め**。「足が速い」で一括処理すると嘘くさくなる。

| 指標 | 内容 | 実装の鍵 |
|---|---|---|
| **wSB** | 盗塁の価値 | 成功率が全て。**損益分岐 ≈ 75%**。走者Steal × 投手クイック(Hold) × 捕手肩で成功確率 |
| **UBR** | 盗塁以外の進塁（単打で1→3、タッグアップ等） | **実は総量が盗塁より大きい**。EV/LA設計の打球落下点＋走者Speed/IQで判断を解く |
| **wGDP** | 併殺回避 | ゴロ時に走者の足で併殺成立率を上下 |

- **BsR = wSB + UBR + wGDP**（WAR式のBsR項をこの本式に差し替える。現状は簡易近似）
- 能力3分割: Speed（足）/ Steal（盗塁技術）/ 走塁IQ（判断）
  - 俊足×盗塁上手×判断良 = 周東型
  - 俊足だが盗塁下手/判断悪 = 宝の持ち腐れ
  - 鈍足だが判断一流 = 損しないベテラン
  - 鈍足×判断悪 = 併殺製造機
- **加齢**: Speedは早く落ちるが走塁IQは残る → 「足は衰えたが走塁で損しないベテラン」が自然に出る

## 7. 守備指標

### 7.1 守備力の構成要素
```
守備力 = Range + Hands + Arm （＋捕手はFraming）
  Range（守備範囲） = ポジショニングIQ + Reaction(初動) + Speed(足)
  Hands（確実性）    = 捕って握り替えて送球完了する（エラー回避）。Range/Armと独立
  Arm（送球）        = Rangeの"後段レイヤー"。到達後の進塁抑止。足し算ではない
  Framing（捕手専用） = ボールをストライクに見せる。近年価値大
```
- **走力と守備範囲はイコールではない**。走力が効くのはRangeのSpeed成分のみ。鈍足でも名手（ポジショニング＋初動）、俊足でも下手な外野手（読めない）が両立する。

### 7.2 OAA（Outs Above Average）— 守備指標の本体
EV/LA設計と接続して解く：
1. 打球生成（方向・EV・LA → 落下点・到達時間）
2. 守る野手の (ポジショニングIQ + 初動 + Speed) から**期待アウト率**を計算 = 届くか
3. 届いたら Hands でエラー判定、アウト走者に Arm で進塁抑止判定
4. 実際の結果 − 期待アウト率 = **OAA**
   - 期待アウト率が低い打球をアウト → **ファインプレー（金枠）**
   - 高い打球を弾く/失策 → **拙守（赤枠）**

- OAA → 守備位置補正して UZR 換算 → **WAR式のUZR項にそのまま差し込む**（骨格は変えない）。

### 7.3 守備能力の加齢
- ポジショニングIQ = 経験・技巧 → **加齢に強い**（鈍足ベテラン名手）
- 初動・Speed → **加齢に弱い**（守備の衰えは足から）
- Arm = 中間、Hands = 安定
- → 「足が衰えレンジは狭まったが、ポジショニングと確実性で一塁コンバートして生き残る」が構造から出る

## 8. 投手モデルと役割

### 8.1 先発適性 = 2軸（比重は球種数が圧倒的主役）
| 軸 | 決定要素 | 意味 |
|---|---|---|
| **巡目耐性（主軸）** | 球種数 | 2球種は2巡目で的を絞られる。3-4球種で3巡目まで持つ |
| **イニング耐性（従）** | スタミナ | 100球投げ切れるか。少数の例外を拾う補助線 |

- **奪三振能力と球種数は独立**。1-2球種でも一級品なら三振は山ほど取れる。
  - 質◎ × 球種多 → エース（先発）
  - **質◎ × 球種少 → 豪腕クローザー**（奪三振は先発以上でも先発不可）
  - 質○ × 球種多 → イニングイーター先発
  - 質△ × 球種少 → 敗戦処理
- ⚠️ 「奪三振が高い＝省エネで先発短命」という因果は**作らない**（いい投手が先発に回らない不自然が起きる）。

### 8.2 先発ダメ→中継ぎで輝く
役割で発現パラメータを切り替えることで、同一人物が先発FIP4.80 / リリーフ3.10 になる：
1. **一巡目効果（最大要因）** — リリーフは1巡しか見せない
2. **全力配分** — 1イニングだけなので球速+1〜2km、得意2球種に絞れる
3. **スタミナ資質** — 3巡持たせる持久力がそもそも無い個体

### 8.3 中継ぎ評価とレバレッジ（WARの死角）
- **WAR（FIPベース）は"場面"を意図的に無視する**（同点9回の1失点も大差の1失点も同価値）。理由: いつ投げるかは投手の責任でない。
- → **「WARの割に勝てない（＝接戦で中継ぎが打たれる）」はWARの死角で起きる**。錯覚でなく指標の構造。
- その死角を埋める既存指標: **WPA（Win Probability Added）/ レバレッジ(pLI) / シャットダウン&メルトダウン**
- **実装**: レバレッジ（接戦度）に応じて好リリーバーを投入する継投AI ＋ WPA集計
  - → 「WARは平凡だがWPA抜群のセットアッパー」が出る
  - → 中継ぎ層が薄いチームは接戦でB級を高レバレッジに晒す → **WAR予測を下回る勝率**（＝現実の"中継ぎ崩壊チーム"が構造再現）
- 継投AIのレバレッジ化は軽実装、WPAは勝率テーブルが要り中実装。

## 9. WAR算出

WARの骨格は既に組んであり、各指標の精緻化は「中身の差し替え」で済む。

### 野手WAR
```
WAR = (wRAA + BsR + UZR + posAdj + repl) / RPW
  BsR   = wSB + UBR + wGDP （§6）
  UZR   ← OAAから換算（§7）
  posAdj = 守備位置補正 × (守備イニング / 1350)
  repl  = (PA / 600) × 13.3   （代替水準）
  RPW   = Runs Per Win
```
- 位置補正の序列（難→易）: `C ≧ SS > CF > 2B ≈ 3B > RF > LF > 1B`（コンバート判定にも流用、§15）

### 投手WAR（FIPベース）
```
FIP     = (13·HR + 3·(BB+HBP) − 2·SO)/IP + FIPconstant
WAR     = ( (lgFIP − FIP)/9·IP + (replFIP − lgFIP)/9·IP ) / RPW
replFIP = lgFIP × 1.216   （代替水準）
```
- 発展: レバレッジで重み付けした投手WAR（§8.3のWPAと併用）

## 10. 加齢・成長・故障

### 10.1 能力別加齢カーブ（総合力を一本のカーブで動かさない）
| 能力 | 加齢特性 |
|---|---|
| 走力・守備（初動/スピード） | 早く落ちる（20代後半〜） |
| パワー（EV） | 遅くまで残る／20代で天井後 維持 |
| 選球眼（四球） | むしろ伸びる |
| コンタクト・三振耐性 | 終盤に悪化 |
| 制球・技巧・ポジショニングIQ・走塁IQ | 加齢に強い |
- 一般カーブ: ピーク26-28、32から本格衰え。**曲線だが1オフシーズンで急落もありうる**。

### 10.2 個体ごとの晩成/鉄人（§12で実例展開）
- 選手生成時に `peakAge` と `declineRate` を**分布から個体ごとに引く**。
- `declineRate` は能力タイプと相関させる（球速・走力低 ＆ 制球・技巧高 → 衰え遅い）。
  - → **技巧派しか長生きできない**縛りがタダで付く（速球派が50歳まで投げる事故が原理的に起きない）。

### 10.3 成長（若手）
- **加齢よりノイズが遥かにデカい**（TINSTAAPP: 投手の有望株は当たらない）。
- 高分散、bust（凡庸に終わる）を多めに。点でなく幅で。

### 10.4 ブレイクイベント（離散的ジャンプ／上下両方）
- 低確率で能力が**階段状に**跳ねる離散イベント。
  - 上方: フォーク習得（球種の列が生える）、覚醒（真値ジャンプ）、EVジャンプ（§12.3）
  - **下方: 制球崩壊（イップス）、故障明けの別人化、燃え尽き** ← §11で必須と明記
- 発火対象パラメータを変えることで、千賀型（球種）も板山型（打撃真値）も用具型（EV）も同じ仕組みで表現。

### 10.5 故障（ハザードモデル）
- 予測でなく確率事象として扱う。年×シーズンの発生確率を以下で上下:
  - **故障歴（最大リスク／再発する）**、年齢、ポジション（捕手は壊れる）、投手の投球量
- **再発**と**後遺**（復帰後に能力一時減）を持たせる。
- 非対称性: **打者は大怪我から戻れるが、投手の一度の大怪我は将来の故障と能力低下の始まりであることが多い**。

### 10.6 生存バイアス（バグでなく現実の再現）
- 弱い選手を引退・解雇で消すと、観測上の加齢カーブが実際より平らに見える。
- 40過ぎまで残る選手＝「衰えなかった個体」だけ → 鉄人が自動でレア化。**そのままで正しい。**

## 11. 見落としがちなパターン（分類）

これまでの「個体の運命」系に加えて、抜けやすい3カテゴリ：

### 11.1 急転落・暴落系（上振れの裏返し）
- 制球崩壊、大型契約直後の暴落、故障明けの別人化、若くしての燃え尽き。
- 下方ブレイクイベント（§10.4）。**上方イベントだけ入れるとリーグがインフレするので、バランス上ほぼ必須。**

### 11.2 文脈で化ける/死ぬ系（選手×環境の相互作用）※費用対効果 高
能力は同じでも置かれ方で結果が変わる。移籍を「化ける/死ぬ賭け」にする：
- **役割転換**: 先発ダメ→抑えで開花（§8.2）
- **パークファクター**: 狭い球場の左打者／広い球場の中堅。同じ打球が本塁打にも凡フライにも
- **起用法/相性**: 対左特化ワンポイント、左右の相性
- **守備位置の玉突き**: 名手に押し出される（出場機会システムの応用）
- → 「真の実力」を1スカラーでなく**文脈ごとに発現が変わる**設計に

### 11.3 集団・時代系（個体を超えたうねり）※長期運用後
- **世代の波**: ドラフト当たり年/外れ年 → 黄金世代
- **球史トレンド**: 投高打低↔打高投低の揺れ、平均球速の経年上昇（リーグ定数をゆっくり動かす）
- **王朝と均衡**: 強い球団が数年続いて崩れる振り子
- **記録の文脈**: 打高時代の.320と投高時代の.290が同価値 → 記録の重みが本物に

> 除外推奨: 盗難サイン・スキャンダル・監督采配などの盤外要素は焦点がボケるので後回し。

## 12. キャリア・ドラマの実装（実例対応）

「三層構造（§1）＋能力別カーブ＋ブレイクイベント＋出場機会」の組み合わせで、専用ロジックほぼ無しに出る。

### 12.1 育成からの這い上がり（千賀・周東型）
- 入団時、球団に見せる値 = `真値 + 評価ノイズ`。**育成枠は評価ノイズを大きく＆下振れ方向**に（だから安く獲れる）。
- **二層ロスター（支配下/育成）＋昇格判定**（育成の観測成績が閾値超で支配下登録）← 這い上がりの"箱"
- 成長ドリフトの裾を広く ＋ ブレイクイベント（球種列が生える＝千賀のフォーク）
- 周東型は「もともと飛び抜けた1ツール（走力）が、活きる起用に後からハマった」＝能力別カーブ＋離散習得

### 12.2 戦力外からの復活（板山・上林・福地型）
- **鍵: 観測成績が出場機会に依存する**。多くの復活は「能力が低かったのでなく出番がなかった」。
  - 上林型: 外野渋滞で打席が回らない→少ない/歪んだ観測でショボく見える→見切り→他球団でフル出場→真値が表に
  - 板山型（不振で切られたが真値は平均級）: 打席ノイズの平均回帰で再現
- **放出判定は"少なく歪んだ観測成績"で下す** → 「ここでは死ぬ/余所では生きる」が構造的に起きる
- チャンネル2系統:
  - ① 戦力外→拾われ: **球団ごとに評価関数を違える**（全球団同目だと復活が起きない）
  - ② 人的補償: プロテクトリスト（例28人）、FA流出球団が獲得球団の非プロテクトから1人。漏れる理由 = (a)評価ミス (b)**枠不足で泣く泣く外した**（福地型は主に(b)、枠の有限性がドラマ）
- **「全員は復活しない」は自動**: 3段フィルタ（大半は真に低い／評価≪真値の個体だけが宝／出場機会を掴めた者だけ開花）
- 頻度ツマミ = スカウト評価ノイズの大きさ ＆ 見切りの厳しさ

### 12.3 覚醒 vs 守備向上（板山 ≠ 山本泰寛の腑分け）
別メカニズムとして書き分ける：
- **板山＝打撃覚醒**: 真値の上方ジャンプ（ブレイクイベント）。実例では**バットを軽量化→スイング効率↑→EV上昇**＋コンタクト改善。
  - 設計判断: EV = 生体Power × スイング効率。効率は用具/メカで動くが、**用具モデルは作らない**。「EVも稀に後天ジャンプしうる」としてブレイクイベントの発火対象にEVを含める程度に留める（内部的には板山型と同機構、原因はモデル化しない）。
- **山本泰寛＝守備向上**: 打撃据え置き（ずっと2割前半）で守備だけ伸びる。**共通素材（足・肩）でなくポジショニングIQ・Hands（経験で伸びる守備スキル）の上昇**。打撃と独立に動くのが肝。「なぜか守備がうまくなった」の"なぜか"は守備が静かで箱スコアに出ないから傍目に唐突に見えるだけ。

### 12.4 晩成・鉄人（和田・山本昌・石川雅規型）
- **和田型（打者晩成）**: EVはほぼ伸びない（生体パワー天井）。伸びるのは**LA最適化（同じ強さの打球を長打角度帯へ）＋方向（引っ張り活用）＋選球眼（強い打球を打てる打席割合UP）**。→ 技術系ツール主軸の打者だけが晩成。
- **山本昌・石川雅規型（投手鉄人）**: 球速（投手のEV相当）は落ちるが、制球（打者を良EV格子に入れさせない）＋球種の出し入れは技巧で残る。**球速が武器でない投手だけが長持ち**。打者の和田とコインの裏表。
- 実装: `peakAge`（後ろズレ）と`declineRate`（ほぼ0の裾）を能力タイプ相関で引く（§10.2）。頻度ツマミ = 衰え速度分布の裾の太さ 一本。

## 13. 守備の詳細（§7の実装補足）

### コンバート
- **〈共通素材〉＋〈ポジション別習熟テーブル〉**の二層で、専用ロジックなしに表現。
- コンバート = 共通素材はそのまま、別ポジションの習熟をゼロから育てる。
- **成否は素材で決まる**:
  - 下り（難→易: SS→2B/3B, CF→両翼）は成功しやすい（難ポジ素材は易ポジで余る）
  - 上り（易→難）は素材不足だと無理
  - 横（3B→1B易、2B→C不可: フレーミング等の特殊技能）
- **加齢コンバート（延命）**: Speed低下→難ポジの実効守備力が閾値割れ→易ポジへ移して延命（SS→3B/1B, CF→両翼）。**球団の判断**として発生させると運営ゲームに。

### ユーティリティ vs 専門職
- 同じ共通素材でも**習熟の"配り方"**で分かれる: 万能型=複数ポジに分散、専門型=一点集中。生成時に方向性を振る。
- **ユーティリティの価値はWAR上は地味だが編成価値がある**（控え1枠減らせる＝ベンチ自由度）。現実通りのねじれ。

### 謎に守備上手い戦力外ユーティリティ（山本泰寛・板山型）— 設計の踏み絵
4要因が一点に交わる:
1. **守備は観測されにくい**（箱スコアに出ない、1年ではUZR/OAAがブレる）→ 打撃偏重の評価関数は**系統的に過小評価**
2. **ユーティリティ起用が観測を二重に薄める**（攻守とも下振れ方向）
3. **素朴な評価が位置価値（posAdj）を拾えない**（.230でもSS守備＋位置補正で実WARは出てる）
4. **編成都合**（渋滞・DH無し・若手優先）で切られる

→ **重要な設計判断: 球団AIを"正しいWAR"で評価させてはいけない。** 全球団が真WARで値付けすると宝が一人もこぼれず、市場が完璧＝つまらない＆非現実的。**球団AIをわざと現実的に間違わせる**（守備・位置を過小評価、打撃のうるさい数字に寄せる）。**歪んだ球団評価と真WARの差分こそが宝の泉。市場の非効率は"仕込む"もの。**
→ そして「守備・位置を正しく重める評価関数を持つ球団」を混ぜると、そいつが**他球団の捨てた宝を系統的に拾う**（守備版マネーボール）。狙わず機能する。

## 14. 投手/野手転向

- 転向は**非対称（一方通行）**で、それをモデルが表現できると本物になる。
- 判定は「共通素材が転向先の要求を満たすか」で決まる（能力素材は登録に依らず常時保持、§2.1）。

| 転向 | 頻度 | 理由 |
|---|---|---|
| 投手→野手 | **多い**（石井琢朗型） | 投手は身体能力エリートの宝庫。球が速いだけで投手にされてた個体が、投手をやめると余った素材で野手開花 |
| 野手→投手 | **稀** | 球速・球種の専用素材が要る。強肩野手がたまに満たす程度 |

- **打てる投手**: 投手登録のまま打撃真値が高い個体。普段は打席が薄く観測されないだけ（分布の右端）。専用フラグ不要。
- **転向トリガー**: 投手→野手は (a)伸び悩み/故障で球速低下 ＋ (b)打撃・走力素材が閾値以上 で発火（故障システムと合流）。球団の判断として起こすと運営ゲームに。
- **大谷＝二刀流は転向でない**（登録排他の前提を破る特殊ケース）→ §20 保留。

## 17. 技術アーキテクチャ

### データ保存（ローカルで十分・むしろ正解）
- 選手1人 ≈ 2KB(JSON)、1000人で約2MB。通算20年でも数十MB。RAM常駐でも余裕。
- **爆発するのは1球/1打球の生ログ**（全試合×全年で数百MB）。対策: **集計値（シーズン/通算）は永続保存、生イベント（EV/LA打球）は最新シーズンぶんだけ保持、古いのは捨てる**。
- 保存技術:
  - ネイティブ（Swift/Kotlin, RN, Flutter）→ **SQLite** or 状態まるごとファイルシリアライズ
  - WebView/PWA → **IndexedDB**（数百MB可）。**localStorageは5-10MB＆文字列のみで力不足、使わない**
  - `window.storage`（アーティファクト）は試作専用、製品版で置換

### 計算負荷（保存より重要）
- 1シーズン＝数百万打席は一瞬〜数秒。多年一括は数秒。
- **UIスレッドを止めない**（Web Worker / バックグラウンドスレッド）＋プログレスバー。

### 決定論RNG
- 線形合同法で**同一シードなら誰が回しても同結果** → 全国対戦のチート検証に必須（§19）。

### クラウドセーブ（自前サーバー不要の裏技）
- iOS: **iCloud（CloudKit / Key-Value）**、Android: **Google Play Games Saved Games**。無料枠、DB運用不要。
- 進め方: **まず完全ローカル → セーブ形式をバージョン付きで綺麗に設計 → 後からクラウドセーブを"乗せるだけ"**。最初からサーバーを背負わない。

## 19. 全国対戦

**朗報: リアルタイム対戦でない（結果が出ればいい＝非同期でよい）。** これがこのジャンルの救い。難所は同期でなく**公平性・チート・バージョン管理**。

| Lv | 内容 | 実装 |
|---|---|---|
| **Lv1** | 非同期ランキング（各自のリーグ結果を送って全国ランク） | BaaS(Firebase/Supabase)で1日。サーバーは受けて並べるだけ |
| **Lv2（本命）** | すれ違い対戦（チームデータを預け、相手データDLして戦わせる） | 相手の"操作"不要、"チームデータ"だけ。**サーバー側でバッチ実行**（夜間総当たり→翌朝結果配布）。放置型リーグ |
| Lv3 | リアルタイム同期（ライブドラフト、同時視聴） | 状態同期・接続管理・切断処理。重い。当面やらない |

### 公平性の3課題（全国対戦が"難しい"の正体）
1. **チート（誰がシミュレートするか）**: 端末計算だと結果改ざん可。対策 = (a)重要な対戦は**サーバー側計算**、(b)端末なら**同一シードで両者計算→突合、不一致を弾く**（決定論RNGが効く）
2. **能力値の捏造**: 最強チーム送信。対策 = サーバーが生成過程の妥当性検証、または**生成自体をサーバー側**で
3. **バージョン地獄**: 係数変更で同じ試合の結果が変わる。**サーバーがエンジンバージョンを固定/強制**（地味に一番めんどい）

### ロードマップ
- ローカル完成 → Lv1ランキング(BaaS) → Lv2すれ違い（最初からサーバー側シミュレートでチート封じ）→ (Lv3は当面なし)
- **既存のNode.jsエンジンがそのままサーバーに置ける**のが強み（工数の山はここ、だが流用可）。

## 付録: 貫かれている設計原則（まとめ）

1. **指標は後付けせず、シミュレートの副産物として湧かせる**（打席・打球の粒度で解く）
2. **能力は一個のスカラーでなく軸ごとに割る**（書き分けたい現実の選手像の数だけ軸が要る）
3. **真値・観測・球団評価の三層のズレがドラマの源泉**
4. **ノイズは消さず正しい大きさで乗せる**（個体は予測不能、集団の分布を合わせる）
5. **加齢は能力タイプ別**（身体系は落ちる、技巧系は残る）→ 晩成・鉄人・コンバートが構造から出る
6. **市場の非効率は仕込む**（球団AIをわざと現実的に間違わせる）→ 宝・復活・割安が湧く
7. **フィルタの多段掛けでレア現象を"稀に"出す**（全員は復活/覚醒/晩成しない）
8. **決定論RNG**（較正の再現性＋全国対戦のチート検証）
9. **描くのは安い(Lv2 SVG)、重いのは画像アセット**
10. **まずローカル完結、サーバーは後から乗せる**
